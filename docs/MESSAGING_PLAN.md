- 未经用户后续明确授权，不重启后端，不运行 MySQL 命令。迁移及部署操作需提供文档。

## 4. 建议表结构

建议采用 5 张核心表，另按需求增加拉黑表。以下为逻辑字段草案，不是可直接执行的 SQL。

所有用户关联字段应与实际 users.user_id 类型一致。新消息主键的类型、时间精度、外键删除策略及索引名称在迁移设计时确定；若使用 BIGINT，接口应以字符串传输 ID，避免 JavaScript 数值精度问题。

### 4.1 dm_conversations：一对一会话

每对用户一条记录：

- id：会话 ID。
- user_low_id：双方 user_id 中较小的一个。
- user_high_id：双方 user_id 中较大的一个。
- last_seq：当前会话最新消息序号，初始为 0。
- last_message_at：最后发送消息时间，可为空。
- created_at：会话创建时间。

约束建议：

- UNIQUE(user_low_id, user_high_id)，避免双方分别发起时创建重复会话。
- 要求 user_low_id < user_high_id，不允许与自己建立会话。
- 后端验证发起者和接收者，不能依靠前端保证成员关系。
- 昵称和头像通过用户资料读取，首版不在会话表中复制。

### 4.2 dm_messages：私信内容

每条消息一行：

- id：消息 ID。
- conversation_id：所属会话。
- seq：会话内递增序号。
- sender_id：发送者 user_id，从登录会话取得。
- client_message_id：客户端生成的 UUID，用于重试去重。
- message_type：首版建议仅 text。
- content：消息正文。
- created_at：服务端记录的发送时间。
- recalled_at：可选，撤回时间；是否支持撤回尚待确认。

约束与发送规则建议：

- UNIQUE(conversation_id, seq)。
- UNIQUE(sender_id, client_message_id)。
- 在同一数据库事务中锁定会话行、分配 seq、插入消息并更新会话时间。
- 并发重复请求需返回已有消息；同一个 client_message_id 携带不同会话或正文时应拒绝。
- 按 conversation_id 和 seq 进行游标分页，支持向上加载历史和重连补取。
- 正文长度限制、消息留存期限和撤回规则待定。

### 4.3 dm_conversation_members：每个人的会话状态

一个一对一会话有两行：

- conversation_id：会话 ID。
- user_id：会话成员。
- last_read_seq：该用户已读到的位置，初始为 0。
- muted：是否免打扰。
- hidden_at：该用户是否隐藏此会话，可为空。
- cleared_through_seq：该用户清空历史到的位置，初始为 0。

约束与行为建议：

- PRIMARY KEY(conversation_id, user_id)。
- 按 user_id 查询会话列表需要相应索引，具体索引结合列表查询确定。
- 建立会话和两条成员记录应在同一事务内完成。
- 仅允许 dm_conversations 中的双方成为成员。
- 已读位置按最大值单调推进，验证上报位置不超过该用户可访问的消息范围。
- 未读数统计对方发送、序号大于已读和清空位置的有效消息；不能简单使用 last_seq - last_read_seq。
- 隐藏和清空只影响当前用户，不删除对方的聊天记录。
- 建议收到新消息时重新显示已隐藏的会话。
- 免打扰只改变提醒行为，仍接收消息并记录阅读状态。
- 是否提供隐藏、清空、免打扰入口，以及是否向对方展示已读状态，尚待确认。

### 4.4 system_notices：官方通知正文

一条通知正文只保存一次：

- id：通知 ID。
- title：标题。
- content：正文。
- category：建议 announcement / account / maintenance 等。
- audience_type：指定用户或全体用户。
- created_by：发布者或后台操作者标识，具体关联方式待确认。
- status：建议 draft / published / withdrawn。
- published_at：发布时间。
- expires_at：失效时间，可为空。
- created_at：创建时间。

行为建议：

- 只有通过后台权限验证的操作者可以发布官方通知。
- 普通用户不能通过提交“官方”类型字段伪造通知。
- 正文格式、链接支持、发布后是否允许修改、管理入口和权限模型待定。

### 4.5 system_notice_recipients：通知接收与阅读状态

- notice_id：通知 ID。
- user_id：接收用户。
- delivered_at：通知进入用户消息列表的时间，不代表手机推送成功。
- read_at：阅读时间，可为空。
- deleted_at：该用户删除通知的时间，可为空。

约束与投递建议：

- PRIMARY KEY(notice_id, user_id)。
- 为按 user_id 查询列表及未读记录配置索引。
- 指定通知只为目标用户插入接收记录。
- 全体通知按发布时符合条件的用户生成接收记录，人数较多时分批投递。
- 唯一约束用于保证批量任务重试不重复投递。
- 批量任务的目标用户范围、任务进度和失败重试需在实施时补充定义。
- 建议新注册用户默认不补发历史公告，该规则待确认。
- 用户规模很大时再评估全体公告共用可见范围、仅保存阅读状态等替代方案。

### 4.6 user_blocks：拉黑关系（建议，待确认）

- blocker_id：发起拉黑的用户。
- blocked_id：被拉黑用户。
- created_at：拉黑时间。
- PRIMARY KEY(blocker_id, blocked_id)，禁止拉黑自己。

需要讨论拉黑是否双向阻止私信、是否保留已有记录、解除拉黑后的行为，以及给发送方显示怎样的提示。

## 5. 消息发送、在线通知与离线推送

建议流程：

1. 验证登录身份、会话成员、拉黑状态和发送频率。
2. 如决定启用内容审核，按明确的隐私与审核规则处理。
3. 在事务中保存消息并更新会话。
4. 提交成功后发送 Socket.IO 实时事件。
5. 客户端根据消息标识去重；断线重连后从数据库补取遗漏消息。

数据库是消息事实来源。Socket.IO 实时事件用于提醒和同步，不能替代持久化；进程可能在数据库提交后、事件发送前中断，因此客户端仍需补拉。若要求服务端可靠重试事件，可在实施时增加事务事件表或可靠任务机制。

“站内消息”与“App 关闭后的手机推送”是两个能力。若需要离线手机通知，还需设计设备推送令牌、平台渠道和 APNs／Android 推送接入，不能把 Socket.IO 当作离线推送方案。

## 6. 隐私与权限（待确定具体产品规则）

- 建议只有会话双方可以读取私信；所有接口和 Socket.IO 房间加入都必须执行服务端鉴权。
- 当前设计为服务端保存、服务端可读取的私信，不代表端到端加密。
- 是否需要端到端加密及多设备密钥同步，用户尚未决定。
- 是否审核私信尚未决定；若使用第三方审核，需要明确说明第三方会接触消息内容。
- 若增加私信图片或附件，应通过鉴权下载或短时授权访问，不能直接沿用公开头像 URL 的访问方式。
- 手机锁屏提醒是否显示正文、拉黑、举报和陌生人联系策略尚待讨论。
- 使用稳定的内部 user_id 关联数据；客户端不能指定或伪造发送者身份。

## 10. 后端接口草案（2026-09-28，待确认）

已确认实施顺序：先进行后端部分。本节是接口建议，尚未实施；不代表用户已经确认匿名身份、陌生人策略、私信审核等未决规则。

现有 NestJS 默认全局前缀为 /node。下面省略该前缀。客户端接口复用 SessionGuard，统一通过 x-session-id 和 x-session-secret 请求头鉴权；不把会话密钥放在 URL 中。发送者、阅读者和接收者权限均由后端根据登录用户判断。

### 10.1 私信：5 个基础接口

- POST /dm/conversations
  - 参数：recipient_user_id（目标身份的具体定位方式待确认）。
  - 创建或返回双方已有会话；返回 conversation_id、对方公开资料和当前用户的会话状态。
  - 自己与自己、无权联系、被拉黑等情况拒绝；并发创建通过用户对唯一约束去重。
- GET /dm/conversations?cursor=...&limit=20
  - 返回当前用户的会话列表、对方公开资料、最后消息摘要、未读数和 next_cursor。
  - 使用稳定的复合排序游标；客户端按会话 ID 合并更新，避免列表更新产生重复展示。
- GET /dm/conversations/:id/messages?before_seq=...&limit=30
  - 获取最近消息或向上分页；返回消息、has_more 和下一游标。
  - 可改用 after_seq 补拉新消息；before_seq 与 after_seq 不允许同时使用。
  - 校验当前用户属于该会话，应用其清空历史范围；普通读取不自动标记已读。
- POST /dm/conversations/:id/messages
  - 参数：client_message_id（UUID）、content；首版按文字消息设计。
  - 返回已保存消息的 id、seq、sender_id、content 和 created_at。
  - 同一用户重试同一 UUID 返回已有结果；同一 UUID 对应不同正文或会话返回冲突。
  - 限长、限频、鉴权、拉黑校验均在服务端完成；审核策略另行确认。
- PUT /dm/conversations/:id/read
  - 参数：last_read_seq。
  - 更新当前用户的阅读位置并返回当前未读数。
  - 只向前推进、不得超过可访问消息范围；多设备旧请求不能覆盖新阅读位置。
  - 用于自身多设备同步；不默认向对方暴露已读回执。

### 10.2 官方通知与未读统计：4 个接口

- GET /notices?cursor=...&limit=20
  - 查询发给当前用户、已发布且未撤回的通知，返回标题、摘要、发布时间和阅读状态。
- GET /notices/:id
  - 查询有接收权限的通知全文；普通查询不自动改变阅读状态。
- PUT /notices/:id/read
  - 标记当前用户已读，重复调用不产生额外效果。
- GET /messages/unread-count
  - 返回 dm_unread、notice_unread、total，供消息页和底栏红点使用。
  - total 采用消息条数之和，产品若希望使用“未读会话数”需另行确认。
  - 计数只包含当前用户可见、未删除／未清空的有效内容。

### 10.3 官方发布端：历史草案（已暂缓）

本节原先列出的 4 个接口已移出当前范围，仅保留讨论记录。后续随管理员版软件重新确定，统一放入管理员接口目录；当前不创建这些路由、发布服务或权限机制。以下是历史草案：

- POST /admin/notices
  - 创建草稿；参数包含 title、content、category、audience_type，以及定向通知的 recipient_user_ids。
  - 返回 notice_id；通知草稿及目标范围需要持久化。草稿目标保存结构是对第 4 节表结构的待补充设计。
- PATCH /admin/notices/:id
  - 修改尚未发布的草稿和目标范围；建议发布后正文不原地修改。
- POST /admin/notices/:id/publish
  - 幂等发布；锁定内容和接收范围，创建可恢复的分批投递任务。
  - 返回“已受理”的投递状态，不能把任务入队直接当作所有用户投递完成。
- GET /admin/notices/:id
  - 查看草稿／发布状态及投递进度、失败情况，便于操作人判断是否完成。
  - 批量投递状态、目标快照和重试信息需要补充到发布任务设计，不仅依赖进程内变量。

通知发布、草稿编辑、投递管理、撤回与重试统一留待管理员版设计。当前不会提供无鉴权的临时发布入口。

### 10.4 拉黑：建议首版同时提供的 3 个接口

- PUT /dm/blocks/:userId：拉黑目标用户，幂等。
- DELETE /dm/blocks/:userId：解除拉黑，幂等。
- GET /dm/blocks?cursor=...&limit=20：查询自己的拉黑列表。

这部分依赖拉黑关系表及双方发送限制规则的确认。不要让创建新会话绕过拉黑检查。

### 10.5 可延后接口

- PATCH /dm/conversations/:id/preferences：免打扰等个人设置。
- DELETE /dm/conversations/:id：仅隐藏自己的会话，具体语义需先确认。
- POST /dm/conversations/:id/clear：只清空自己的历史可见范围。
- POST /dm/messages/:id/recall：撤回，依赖时限、提示和留存规则。
- 批量已读：需携带明确的已见范围／截止点，避免误读并发到达的新消息。
- 私信附件上传与鉴权下载。
- 手机推送设备注册及注销。
- 举报、会话邀请和陌生人接收设置。

### 10.6 Socket.IO 事件建议

在 HTTP 之外建议提供 dm.message_created、notices.created，以及面向用户自身设备的 messages.read_updated。

- 连接通过现有会话凭证验证，房间由服务端绑定当前用户。
- 消息先写入数据库，事务提交后发事件。
- 事件携带可去重标识；掉线后通过 HTTP 接口补拉，不能只依赖即时推送。
- 系统公告分批投递时，用户接收记录落库后才向该用户发送事件。
- 不向未授权用户推送会话正文，也不允许客户端任意加入其他用户房间。

### 10.7 接口共同约定

- 移除管理员端后，当前用户端基础建议为 9 个接口；如果一并实现拉黑，则为 12 个。具体业务规则仍待确认。
- 限制 limit 的最大值；使用游标分页，不一次性返回全部历史。
- 客户端不得提交可信 sender_id、官方身份或其他用户的阅读状态。
- 不向普通消息接口返回手机号、令牌、设备凭证等用户私密字段。
- 未登录返回 401；无权访问的私信／通知建议统一返回 404，减少资源存在性泄露；频率限制返回 429；幂等键冲突返回 409。
- 应返回稳定的业务错误码及可展示的中文消息，前端普通反馈统一使用小 Toast。
